## Exploratory (not pre-registered)

**1. For closed models, both fixes remove duplicates entirely.**
- Episodes with any duplicate effect, out of 360:

  | A | B | C | D | N |
  |---|---|---|---|---|
  | 91 | 0 | 0 | 3 | 0 |

- An atomic scope removes the duplication that defines the keys hazard.
- C's remaining harm is mostly partial work **left in place**: for example, an agent orders the
  missing monitors separately instead of replacing the incomplete order, which fails the
  scenario's `no_partial_orders` invariant. That is a recovery-quality problem, not
  duplication.
- So the scope result holds in the narrow sense, and N1 fails for a different reason: the agent
  still has to repair the partial state.

**2. The generated description for the atomic scope backfired, mostly for open models.**
- Arm D's text says a retry with the same key is never executed again, and to reuse the key
  when retrying.
- Agents then checked state much less before retrying (52% vs 90% in C). That is harmless in
  itself, because the replay is safe.
- But after the service replayed the partial failure, many agents re-placed the *whole*
  request with a **new** key, repeating the committed part. This is the route the
  pre-registration anticipated.
- Open-model episodes with duplicates: 84 of 270 in D, vs 26 in C.
- **Interpretation:** a description that tells agents a retry is safe, without telling them how
  to repair a partial outcome, lowers their guard at the wrong moment. Better wording is
  possible (e.g. "after a partial failure, complete or undo the committed part; don't resend
  the whole request"), but it would be a new hypothesis.

**3. Open models are dominated by key discipline, not scope or wording.**
- Under a hidden write with keys offered, open models were harmed in 72% of episodes (86/120)
  under either scope, vs 1/160 and 0/160 for closed models.
- That matches open-confirm: they rarely key the first write, so neither the service's scope
  nor the description can help.
- Only the runtime, which attaches keys itself, protects them.

**4. The substitute DeepSeek-V4.1-Flash-1017 barely showed the hazard:** 0–2% harm in every arm
([supplement](../contracts-supplement-20261027-090006/NOTES.md)).

## What this means for the paper (Q4)

- **The bounded keys claim holds:**
  - The hazard is a mismatch between what the key covers and what its description promises.
  - Fixing either side removes the duplication for capable models: an atomic scope, or an
    accurate contract-generated description.
- **But the agent still has to handle partial outcomes well,** and how a description is worded
  can make that worse.
- **This strengthens the paper's allocation claim:** execution recovery belongs to the runtime,
  which had 0% harm under every contract tested, not to agents reading descriptions.
